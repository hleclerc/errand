# `@errand.memo`: a result kept by its inputs, in the project's cache

ADR 0012 gave a project cache zones, which both sides add to and nobody replaces. ADR 0013 put
downloaded files there, named by their contents. The same holds for a result that takes long to
compute (an otrec reconstruction, a reference solution, an expensive preprocessing step): named by
what it was computed from, it never conflicts. Computed on lmo, it comes back here with the cache's
pull, and goes to every other copy with the next push. Nobody computes it twice.

Each project writes this by hand today, with a key it builds itself, a format, and a directory that
errand neither carries nor knows.

## Decision

```python
@errand.memo( version = 2 )
def reconstruct( sino, n_iter = 500 ): ...
```

**The key** is a hash of:
- the function: its module and qualified name;
- `version`: raised by hand when what the function means changes;
- its arguments, bound to its signature, defaults included (a changed default is a new key), minus
  the names in `ignore = [ "verbose" ]`.

Arguments are hashed by what they hold, the same way on every machine: `None`, booleans, numbers,
strings, bytes; tuples, lists, dicts, sets; dataclasses and enums; numpy arrays and scalars, and
arrays of jax or torch, by dtype, shape and bytes; a `Path` by its contents (a file) and its name.
An object can say its own key (`__errand_key__()`). Anything else is an error that names the
argument and says how to get past it (`key = lambda …`, `ignore`, `__errand_key__`). It never falls
back on `repr`, which would hold addresses or nothing at all.

**The function's code is not part of the key**, unless `source = True` adds its source. A hash of
the source misses the functions it calls, and would look safer than it is. `version` is what says it.

**Where.** `errand-cache/memo/<module.qualname>/<key>/`, in the cache zone every project has
(ADR 0013): `value.npz` for an array, or a tuple, list or dict of arrays, `value.pkl` otherwise,
and `meta.json` (the function, the version, the arguments in short, the machine, the date, how long
it took). `save( value, directory )` and `load( directory )` replace the formats (HDF5, a checkpoint).
A result is written in `.errand-work`, which no sync carries, then renamed into place whole.

**Once.** A lock per key: a second run that wants the same result waits for the first, then loads
it. The lock is touched while the computation lasts, so a long one is not taken for a dead one.

**What it says.** `errand.step`: `reconstruct: computing`, then `reconstruct: from the cache
( lmo, 2026-11-18, 41 min )`.

**When it cannot.** A value that does not load (a pickle from another version of a library) is
computed again, and said. Outside a project (no `errand-*.py` above), the function runs, nothing is
kept, and that is said once. Outside errand, in a project, it works the same: the same cache.

**Turning it off.** `errand.memo.mode = "off"` (compute, keep nothing) or `"refresh"` (compute, and
replace what is kept here), or `ERRAND_MEMO=off|refresh`. A refreshed result that the other side
also holds, with other bytes, is a conflict that the sync reports (ADR 0012): the other side keeps
its own until it is removed there.

**Conflicts** mean that the same inputs gave other bytes: a computation that is not deterministic
(a GPU, threads). The first one written stays on each side, and the sync says so. This is no error.

## Considered options

- **A hash of the function's source, by default.** It misses what the function calls, and
  changes with a comment. Offered, not default.
- **`repr` as a fallback for what cannot be hashed.** It holds addresses, or says nothing of the
  contents of an object. An error that says what to do is better than a wrong hit.
- **joblib.Memory.** It does most of this, but its cache is not errand's zone, its keys depend on
  the machine's paths, and it is a dependency that `import errand` cannot carry.
- **A zone of its own for results that stay over there.** Results of several GB all come back here
  after each command. Not done until a project needs it; a `back = False` on `memo` would then say
  which.

## Consequences

An expensive function is computed once across all the machines that run it. The cache here grows
with what every machine computed. Pruning it is by hand, on each side, as for any cache. A bad
`version` (not raised when it should be) gives a stale result: the meta says when and where it was
made, which is how it is found.

## Order of work

1. `errand.memo` (Python): the key, the formats, the lock, the steps, the modes. Tests.
2. otrec: its expensive steps decorated.

Step 1 done on 2026-11-18 (`errand/memos.py`, `tests/test_memo.py`). One thing the tests showed:
errand imports a file under a module name of its own, and a script run by hand is `__main__`, so a
function is named by its file from the project root, not by its module, and that name is in the
key: the same result is found run either way. Arrays checked with numpy in `loom-numpy` (the
suite's own environment has none). Not tried over `Ssh` yet: the cache zone it uses is the one
`errand.download` uses, tried on lmo.
