Servers kept while used: errand serve ​

bash
errand serve --gpus 1 --gpu-ram 10G -- ollama serve     # started if need be; prints its address
errand serve                                           # the services of this machine
errand serve stop ollama

Some work is a server: an LLM that answers an application, a viewer that serves the frames of a run. It should start when somebody asks for it, never twice, stop when nobody uses it, and, on a machine shared with computations, hold its share of the card only while it works.

errand serve does that. The server runs under a keeper, a process of this machine's agent that outlives the command that asked for it: it is listed by errand status, stopped with the rest, and never left behind. Its share of the machine goes through the queue, like a run's.

  • Started on demand, never twice. Two errand serve at once start one server.
  • Stopped when nobody uses it: after --idle ( 10 minutes by default ) with no connection open and the server not busy.
  • Its share given back while it rests. In use, its claim is firm. Idle, it is kept warm: a computation that needs the card asks it to go, and it goes.
  • One address, kept. The port is chosen once for the name and kept, so a client, a tunnel or a bookmark keeps working from one start to the next.

Two sides, errand in between ​

Each port of a service has two sides.

  • The announced side is where clients connect. errand listens there itself, from the first errand serve until the service stops, whether the server is up or not. A connection that comes while the server waits for its share of the card is accepted and held, then relayed once the server answers. This side is yours to fix ( 11435 ), or errand chooses it once and keeps it for the name.
  • The server's side is where the server listens, on 127.0.0.1. Only errand connects there. errand gives it to the server as {port:NAME} in its command and its environment, chooses a free one at each start, or takes the one you fix.

errand sits between the two to see every connection: that is how it knows the server is used whatever its protocol, holds connections while the card is taken, and closes those from other accounts.

Both sides can be fixed, but they cannot be the same number: errand listens on one and the server on the other. To have the server where its clients expect it ( Ollama's 11434 ), fix the announced side to that number, and let the server's be chosen.

Ad hoc, or declared ​

On the command line, the server's command after --:

bash
errand serve --name ollama --gpus 1 --gpu-ram 10G --idle 10m --port 11435 \
             --busy-if 'curl -s localhost:{port}/api/ps | grep -q "\"name\""' \
             -- env OLLAMA_HOST=127.0.0.1:{port} ollama serve

Or declared once, in ~/.config/errand/services.py ( it belongs to a machine and a user, not to a project ), or in any errand-*.py of a project:

python
# ~/.config/errand/services.py
import errand

errand.services[ "ollama" ] = errand.Service(
    [ "ollama", "serve" ],
    env   = { "OLLAMA_HOST": "127.0.0.1:{port}" },
    gpus  = 1, gpu_ram = "10G", label = "ollama",
    busy  = errand.http_json( "/api/ps", lambda r: bool( r[ "models" ] ) ),
    idle  = "10m",
    ports = 11435 )            # leave it out: errand chooses one, once, and keeps it
bash
errand serve ollama         # its address, once it answers

{port}, in the command and in env, is the server's side of the port; $PORT holds it too. The cards granted are given as a run gets them ( CUDA_VISIBLE_DEVICES... ).

Several ports, named ​

A server that listens on several ports names each of them; the command gets each one's server side as {port:NAME}, and the environment as $PORT_NAME:

python
errand.services[ "triton" ] = errand.Service(
    [ "tritonserver", "--model-repository", "/models",
      "--http-port", "{port:http}", "--grpc-port", "{port:grpc}", "--metrics-port", "{port:metrics}" ],
    gpus  = 1,
    ports = { "http":    8000,          # announced 8000, the server's chosen at each start
              "grpc":    "8001:18001",  # both fixed: announced 8001, the server on 18001
              "metrics": None } )       # both chosen, the announced one kept
bash
errand serve triton                 # triton  http http://127.0.0.1:8000  grpc http://127.0.0.1:8001  metrics ...
errand serve triton --url grpc      # http://127.0.0.1:8001
errand serve --port http=8000 --port grpc=8001:18001 -- tritonserver --http-port {port:http} ...

A port is "ANNOUNCED:SERVER", either side left empty for errand to choose ( ":18001", "8000:" ), an int for the announced side, or None. A single port without a name is called port, and {port} is its server side; with several, {port} alone is refused, and so is a {port:NAME} that names none of them, when the service is declared rather than when it starts. A fixed server side that is already taken stops the start with port grpc: the server's side, 18001, is taken.

The service is in use as long as a connection is open on any of its ports; ready, by default, is every port answering.

Only your connections ​

On 127.0.0.1, a port is open to every account of the machine. errand closes, at once, a connection that comes from another account: on Linux it reads, in /proc/net/tcp, which uid opened it. A tunnel of yours ( ssh -L, errand serve connect ) is yours, and passes. keeper.log notes each one closed.

python
errand.Service( ..., others = True )      # every account of the machine may connect

--others on the command line. Elsewhere ( macOS, Windows ) errand cannot tell, and relays every connection; the server's own access control is then the protection.

The server's side is not guarded this way: another account that finds it connects to the server directly. It changes at each start, unless fixed. A server that can listen on a Unix socket, or run in a network namespace of its own, closes that door too; errand does not do it for you yet.

Ollama, from start to answer ​

Clients talk to the announced port ( 11435 here, or the one errand chose and kept ), never to {port}: that is the server's side, and changes at each start.

bash
$ errand serve ollama
ollama  http://127.0.0.1:11435  ( warm )

$ curl -s http://127.0.0.1:11435/api/generate \
       -d '{ "model": "qwen3:14b", "prompt": "Why is the sky blue?", "stream": false }'
{"model":"qwen3:14b","response":"Sunlight scatters off air molecules...", ...}

Without a port =, errand chooses one the first time and keeps it. --url prints only the address, for a script, and starts the server if need be:

bash
export OLLAMA_HOST=$( errand serve ollama --url )     # http://127.0.0.1:41873, the same at each start
ollama run qwen3:14b "Why is the sky blue?"            # the ollama command line is a client too

From Python, with the ollama package or anything that speaks HTTP:

python
import subprocess, ollama

url = subprocess.check_output( [ "errand", "serve", "ollama", "--url" ], text = True ).strip()
client = ollama.Client( host = url )
print( client.generate( model = "qwen3:14b", prompt = "Why is the sky blue?" )[ "response" ] )

From your laptop, through ssh, to the same announced port:

bash
ssh -N -L 11435:127.0.0.1:11435 lmo &      # once; then http://127.0.0.1:11435 here
ssh lmo errand serve ollama --ensure       # started if need be ( or `connect`, below )

What follows, on lmo's card:

text
waiting      the card is held by a computation: the claim waits its turn, a request waits with it
starting     ollama serve, until its port answers ( a few seconds of GPU discovery )
in use       a request is open: the claim is firm
busy         no request open, a model still loaded ( OLLAMA_KEEP_ALIVE, 5 min by default )
warm         nothing loaded: a computation that needs the card evicts it, in about a second
stopped      after `idle` warm, or evicted

OLLAMA_KEEP_ALIVE sets how long a model stays loaded after its last request, and so how long the server stays busy; idle counts after that. Point OLLAMA_MODELS at the models already pulled ( /usr/share/ollama/.ollama/models for a system install ) to use them without a copy.

How errand sees that it is used ​

Every connection goes through the keeper: errand listens on the announced port and relays each connection to the server. So it counts the open connections itself, on every system.

  • A connection open means used, silent or not: a server that thinks for an hour before answering is not abandoned.
  • The probe saying busy means used, with no connection: Ollama with a model loaded. busy is a function of the port ( errand.http_json( path, predicate ) for a JSON endpoint ) or --busy-if, a shell command that exits 0 when busy. A probe that fails or does not answer counts as busy: a saturated server is in the middle of something.
  • Neither: the idle clock runs, and starts again from zero at the next connection.

Throughput is never looked at. A client that keeps a connection open for nothing ( an HTTP keep-alive ) keeps the server longer: the risk is taken on that side, never killing a computation.

Waiting for its share ​

A service that waits for a card waits in the queue like any run, in order: the queue is first come, first served, for everybody. Meanwhile its port is already open: a connection that arrives is accepted and waits, then is relayed once the server answers. The keeper gives up the wait when nobody waits for it any more ( no connection, no errand serve waiting ) for idle.

It stops ​

  • after idle without connection nor busy;
  • warm, when a computation needs its share ( errand queue shows it kept warm: gives way );
  • with errand serve stop NAME, or Ctrl-C under errand serve -f;
  • when the server ends by itself. It is not restarted: the next errand serve starts it again.

It is stopped as everything errand starts: INT, then TERM, then KILL after grace ( 10 s ), on its whole process group. Then its claim is released.

Through ssh: connect ​

bash
errand serve connect ollama

ensures the service, then relays this process's stdin and stdout to it ( connect ollama PORT for another port than the first ). It is what a key in authorized_keys forces, for a tunnel that starts the server when it is used:

text
command="errand serve connect ollama",no-pty ssh-ed25519 AAAA… boucles@laptop

Seen ​

text
$ errand serve
  ollama           busy       127.0.0.1:11435    1 connection
$ errand status
running   ( on lmo: this machine )
  lmo: service ollama busy  127.0.0.1:11435, 1 connection
$ errand queue
  ollama ( service )  gpus=1, gpu_ram=10G  gpu 0  12 min  pid 4121

errand hold ​

A claim held for a process that is not a run, for as long as its input stays open:

bash
errand hold --gpus 1 --gpu-ram 10G -n "my server"

prints granted 0 ( the cards ) once it has it, reads warm ( it may give way ) and busy ( it may not ) on its input, prints evict when a computation needs the room while it is warm, and releases when its input closes. errand serve is built on the same claim; hold is for whoever wants to drive it themselves.

What it does not do ​

  • The queue is per user and per machine. A server started under another account ( a systemd service ) is not seen, and its share of the card is not counted. Nor is a run started with --no-queue: it takes the card without asking, and a service that loads a model next to it may find the card full.
  • The server's side of a port is open to every account of the machine, and so is the announced side outside Linux ( see Only your connections ).
  • From another machine: errand serve connect through ssh, or an ssh -L tunnel to the announced port. A port forwarded through errand's own connection is planned.
