Sharing a machine ​

bash
errand run make -j16                  # shared: waits only if the machine is full
errand run -x ./bench --n 1e7         # a benchmark: the machine to itself
errand run --cpus 8 --ram 16G ./solve # what it needs, so neighbours can be let in
errand run --gpus 1 python train.py   # one card, and told which
errand run --gpu-ram 30% python a.py  # 30 % of a card: three such runs share one
errand queue                          # what the machine has, and what holds it
errand wait                           # return once nothing holds it

A timing taken while something else ran is not a timing. So every errand run takes a claim on the machine it runs on, and the claims of every errand on that machine — two terminals, two projects, the same user — are counted together.

Any command, under the queue ​

Every run takes a claim, shared unless asked otherwise. It runs once the machine has room for it, on this machine or on the one its --env leads to:

option
-x, --exclusivethe machine to itself. What a measurement wants
--cpus N, --ram 8G, --gpus Nwhat it needs, counted against what the machine has
--gpu-ram 40G, --gpu-ram 75%what it takes on each of its cards: a size or a share. Without it, cards are taken whole
--ranks Nthat many MPI processes, each needing the above ( Several processes )
--no-queuedo not wait, and hold nothing
-n, --label NAMEits name in errand queue
-m, --mem 8Ga memory ceiling: past it, the command is killed, not the machine
-l, --log FILEits output goes there too
-qno banners

A run with no -x and no resources holds a shared slot: it waits only while an exclusive run holds the machine or waits for it. An exclusive run waits for what is already running, then holds everything back while it runs.

Three ways to ask, one claim ​

From the most general to the most precise, each one over the one before:

  • The environment says what every run in it takes, known before anything starts:

    python
    errand.envs[ "gpu" ] = errand.Env( [ errand.Micromamba( "jax" ) ],
                                   needs = { "gpus": 1, "gpu_ram": "75%", "ram": "16G" } )

    Jax on a GPU takes 75 % of its card at its first array, whatever the run. needs takes cpus, ram, gpus, gpu_ram and exclusive. It also sizes the allocation of a Slurm layer.

  • The command line, as above: --gpus 1 --gpu-ram 40G, -x.

  • The code, while it runs: errand.require( gpus = 1, gpu_ram = "75%" ), called early, before what it protects is allocated ( for Jax, before import jax ). It never shrinks the claim. → The run asks, from its code

The memory of a card ​

gpu_ram is what a run takes on each of its cards: a size ( 40G ) or a share of the card ( 75% ). The queue counts it per card, as it counts ram per machine: two runs that each take 30 % share a card, two that take 75 % do not. A run with gpus and no gpu_ram takes its cards whole, and a card somebody has a share of is not whole. A gpu_ram alone asks for one card.

A card's size is read with nvidia-smi ( or rocm-smi ) when the queue reads the machine. When nothing says it, gpu_ram takes the card whole. Of the cards that fit, a run is given those with the most left: two runs that share no card do not slow each other down.

The run asks, from its code ​

python
import errand
errand.require( gpus = 1, gpu_ram = "75%" )     # waits until the claim holds it
import jax

errand hands each run the path of its claim ( ERRAND_CLAIM_FILE, beside ERRAND_CLAIM ). require grows that claim, under the queue's lock, and waits until it fits. Once granted it sets CUDA_VISIBLE_DEVICES ( and the HIP / ROCR ones ) in its own process, which a framework reads at its first use of the device, and returns the cards. A require that asks for no more than the claim holds returns at once.

In all, or more. By default require asks for that much in all: what the run already holds counts. require( ram = "20G" ) on a run started with --ram 16G grows it to 20G, not 36G, and require( gpus = 1, gpu_ram = "50%" ) on a run that holds a card at 75 % returns at once. With extra = True ( --extra from the command line, .extra = true in C++ ) it asks for that much more than the run was started with by its environment and command line, and several such calls add up: gpus more cards, gpu_ram more on each card it holds. A share and a size are compared, or added, on the smallest card the run holds. Either way, a claim never shrinks.

A claim that grows is ahead of any new claim, as an exclusive request is. Two runs that grow at once can wait for each other, each holding what the other needs: the younger is then stopped by its require ( errand.Rerun ), and run again, once, with its needs up front. It says so in its output. More generally, a claim that grows and waits makes way for an older one that waits only for the younger growers: three benchmarks under -j, each growing to the whole machine, run one after the other.

Cards asked on a machine that has none are not waited for: the same environment or code runs on a laptop as on a workstation with a GPU.

Outside errand, with --no-queue, or in an allocation of Slurm, PBS, OAR… that errand does not hold, require does nothing and returns at once: a program run by hand never waits, never fails, and sees its environment unchanged.

From another language, errand require does the same and prints what to set:

bash
eval "$ERRAND_STEPS_SH"          # in a shell script: step, view, download, require
require --gpus 1 --gpu-ram 75%   # waits, then exports CUDA_VISIBLE_DEVICES…
text
$ "$ERRAND_PYTHON" -m errand require --gpus 1
CUDA_VISIBLE_DEVICES=1
HIP_VISIBLE_DEVICES=1
ROCR_VISIBLE_DEVICES=1
ERRAND_CLAIM=1

It prints nothing outside errand, and exits with 75 when it was stopped to run again.

In C++, the header errand/require.hpp ships with errand ( header-only, C++17 ). A runner's build line finds it with {errand_include}:

python
errand.runners.replace( errand.Catch2( dir = "cpp", build = "c++ -std=c++17 -I{errand_include} … -o cpp/test_gpu" ) )
cpp
#include <errand/require.hpp>

errand::require( { .gpus = 1, .gpu_ram = "75%" } );    // C++20; in C++17, fill an errand::Needs

It calls errand require, sets what it prints in the process, and returns the cards. Stopped to run again, it throws errand::Rerun: let it go through, or exit.

Remembering what a run required ​

What a run's require calls came to, in all, is always written in its record ( required ). With

python
errand.configure( remember_needs = True )

it is also kept in the machine's state, by environment and target: errand-outputs/state/needs.json. The next run of that target then claims it before it starts, as if it had been on the command line, and says so. The total is kept, not the calls: an extra call is not added a second time on top of what was claimed up front.

text
  claimed up front, as it required last time: gpus=1, gpu_ram=75%

It then rarely grows while running, and its cards are known from its first line. A target that no longer calls require drops what was remembered after one run. Each machine learns its own: another machine, another capacity. It is off by default: every run then asks again, and what it claims is only what the environment, the command line and its code say.

Looking at the queue ​

bash
errand queue
text
The machine (gpu-box)
  has  cpus=32  ram=128000M  gpus=2
  nightly  the whole machine  412s  pid 81233
  train.py  gpus=1  gpu 0  35s  pid 81502
  fit.py  gpus=1, gpu_ram=30%  gpu 1  12s  pid 81544
  win  cpus=4, ram=8192  1204s  pid 80122  ( kept warm: gives way )
  /run/user/1000/errand-queue-1000-gpu-box

errand wait returns once nothing holds the machine and nothing waits for it: the end of a script that must not start before the benchmarks are done.

First come, first served ​

Every request that waits is recorded, and the oldest goes first: whatever arrives after a queued request waits behind it, even when it would fit now. Otherwise a steady stream of small runs would starve a benchmark, or a service waiting for a card, for ever. A claim waiting to grow ( errand.require ) is ahead of everything. A request whose process is gone is dropped at once.

A card is assigned, not merely counted ​

A run that asked for gpus = 1 is told which card, through CUDA_VISIBLE_DEVICES ( and HIP_VISIBLE_DEVICES, ROCR_VISIBLE_DEVICES ). Two runs that both asked for one get different cards; counting alone would let both use the first. An exclusive run gets all of them.

Claims nest: a process that was itself given cards 2 and 5 sees them as 0 and 1, and hands 0 and 1 down.

Kept warm, and giving way ​

What is only kept warm — a Windows virtual machine nobody uses at the moment, a process that has imported torch ahead ( Preload ) — holds a claim that gives way. A run that would fit without it asks for the room and gets it at once, and the warm thing goes. errand queue marks those claims as kept warm. → Agents and keeping warm

Memory ceilings ​

With -m 8G, where the user's systemd bus allows it, the command runs in a systemd-run --user --scope with MemoryMax set: a runaway allocation takes down the command, not the machine. Without a bus ( over ssh, from cron ) the command still runs, without its ceiling.

Stale claims are reclaimed ​

A claim is touched every few seconds while its work lives. One that has not been touched for half a minute is reclaimed, and its owner, if it ever comes back, is told it lost it. That is how a killed run is told apart from a long one.

Waiting is not part of the run ​

duration_s in the record counts the work, not the time spent waiting for the machine: a benchmark's numbers must not depend on who else was around.

An errand inside an errand ​

A run started by another run inherits its claim instead of queueing. The parent holds its claim while it waits for the child, so a child that queued would wait for itself.

Inside a batch allocation ​

In a Slurm allocation that errand keeps warm, the allocation is the machine: errand's queue shares it out between the commands that run in it, with a queue per allocation.

In any other batch job — a Slurm job you submitted yourself, or another scheduler's, recognized by its variables — errand does not queue at all. The scheduler has already decided what this process may have, and a second queue would only wait for itself.

Where the queue lives ​

One queue per user and per machine: a directory of claims in $XDG_RUNTIME_DIR, else the temporary directory, named after the machine. No daemon. A home shared over NFS never merges two machines' queues.
