Ssh: running elsewhere ​

python
Ssh( host, root = None, python = "python3", options = [ ], also = [ ],
     errand_outputs_directory = None, user = None, jump = None )

Everything after it runs on host. The project is pushed there before the command, and what the command wrote is brought back after it. Both go through errand's agent over there, so that machine needs ssh and a Python, nothing else.

python
# errand-envs.py
import errand

errand.envs[ "box" ] = errand.Env( [ errand.Ssh( host = "gpu-box", root = "/home/me/proj" ),
                                     errand.Apptainer( image = "containers/cuda.sif", recipe = "containers/cuda.def" ) ] )
bash
errand run --env box -o python train.py
text
box · 1 entry  box@gpu-box
▸ python  python · args=train.py
  │ epoch 1  loss 0.41
PASS python  12 min 03 s

The push before and the pull after are said at the bottom of the terminal while they last ( ↑ sync push → gpu-box:/home/me/proj · 3 s ), then gone: what they came to — files, bytes, seconds — is in the run's journal, steps.jsonl ( Results and records ).

It must be the first layer: errand.Env() refuses a stack where it is not.

hostwhat ssh reaches: a name from your ~/.ssh/config, or user@host
rootwhere the project goes over there. Default: the same path as here
pythonthe interpreter to try first over there, when no later layer chooses one ( below )
optionspassed to ssh: a port, an identity
userthe login over there, when host does not say it ( User in ~/.ssh/config )
jumpa gateway to go through, or a list of them in order ( ProxyJump in ~/.ssh/config ): "me@gate.example.org". See below
alsosibling checkouts the work needs ( [ "../loom" ] ), pushed to the same relative place over there
errand_outputs_directorywhere errand writes for the project over there: runs, builds, state. Say /scratch/me/proj-out; the project's copy then holds a symlink errand-outputs to it. See Where errand writes

Nothing to install over there ​

errand needs nothing installed on the other machine:

  • Its sources travel. The package is copied to ~/.cache/errand/src/<version>-<checkout>/, one copy per checkout here, and started from there. The errand that answers is the one that asked.
  • It finds a Python to start on. When a later layer chooses the interpreter ( Venv, Micromamba, Uv, a container ), that one. Otherwise it looks where the command starts, after Module, Nix or Vars: the python named here, then python3, python3.14 … down to 3.8.
  • Or it makes one for itself. With none recent enough, it makes one for errand alone in ~/.cache/errand/python: with uv if the machine has it, else micromamba, mamba or conda, else with a uv fetched from astral.sh into ~/.cache/errand/uv. Nothing is put on the PATH, no shell profile is touched. A couple of seconds, once.
text
  errand: no python >= 3.8 here: making one for errand alone, in /home/me/.cache/errand/python
  errand: neither uv nor micromamba nor conda: fetching uv into /home/me/.cache/errand/uv

Under a scheduler, the command starts on a compute node that may have no network. The search is then made once on the machine ssh reaches, before submitting, and the job finds the result in ~/.cache, in the home directory the nodes share.

Everything errand made for itself is in ~/.cache/errand: removing that directory undoes it. ERRAND_CACHE_DIR, set in your shell profile over there, puts it elsewhere: see Where errand writes.

One connection, kept ​

The first command to reach a host starts an agent there, through one ssh. Every later command goes through it, the pushes and pulls included, and nothing logs in again. Here, a hub keeps the connection open between commands. Past the layers, a second agent runs with the environment's own interpreter, inside the micromamba environment, the module, the container: the layers are entered once, not once per command. All of them stop on their own after 15 minutes unused.

What the agents start writes its output to disk over there, so a dropped connection or a closed laptop loses nothing: errand attach follows the work again.

→ Agents and keeping warm

The paths are computed before the run happens ​

The same rules, applied to the same command, give the same paths on both sides. Over there, before anything runs, the preparation writes a plan that names the directories the command will write. Only those come back: the runs of this command in errand-outputs/runs/, the directories asked for with --pull, and the backzones. The rest of the remote tree, which holds other runs from other days, stays where it is.

A grid is expanded over there too, one plain run per combination.

Through an interactive shell ​

ssh runs commands non-interactively, and so never reads the rc file that puts micromamba, cargo or nvm on the PATH. errand runs the remote command through an interactive shell ( $SHELL -ic ), which reads it. That is the difference between micromamba -n myenv run working over there and not.

options go to ssh ​

python
Ssh( host = "gpu-box", root = "/home/me/proj",
     options = [ "-p", "2222", "-i", "~/.ssh/bench", "-J", "jump.example" ] )

A port, a jump host, a StrictHostKeyChecking you have decided about. They reach the agent over there, which every push and pull goes through: nothing else logs in.

A gateway on the way ​

A cluster is often reached through a gateway. ~/.ssh/config can say so, but then an environment file only works for whoever has the same entries. user and jump say it in the file itself:

python
Ssh( host = "frontend", user = "me", jump = "me@gate.example.org", root = "/home/me/proj" )

is ssh -J me@gate.example.org me@frontend. jump takes a list for several gateways, gone through in order. Names are resolved from the last gateway: frontend may be a name only the inside knows.

The project crosses by sync ​

The project is pushed by a sync by manifest, through errand's agent over there: only what changed crosses ( 0.7 s when nothing did ), what a run made over there is never deleted, and what a run writes into the copy is declared once as a zone ( back, build, cache ). → Smart sync

Building over there ​

An image is built where it is used: the recipe is a file here, it is copied over, and apptainer build runs on that host with fakeroot and scratch as declared. Where that host has no internet, build_on = errand.Ssh( ... ) builds it on a machine that has some, and copies the image over ( see Apptainer ).

Adding an allocation ​

Slurm goes between the machine and the container, in the order you would say it: that machine, an allocation on it, the container inside it.

python
# errand-envs.py
errand.envs[ "cluster" ] = errand.Env( [ errand.Ssh( host = "login.hpc", root = "/home/me/proj" ),
                                         errand.Slurm( time = "2:00:00" ),
                                         errand.Apptainer( image = "containers/cuda.sif" ) ] )

Results are pulled, not pushed ​

A finished remote run stays over there until something collects it: the command you wait for, as its last step, else errand attach, errand status or errand watch. → What comes back

What only this machine can supply ​

A host name you can reach, a partition you may submit to: none of it can be committed, none of it can be invented. It goes in an untracked errand-vars.py, read first, and the files read after it ask for it with errand.value, which takes a default:

python
# errand-vars.py -- not tracked
ssh_host = "gpu-box"
ssh_root = "/home/me/proj"
python
# errand-envs.py
import errand

errand.envs[ "box" ] = errand.Env( [ errand.Ssh( host = errand.value( "ssh_host", "gpu-box" ),
                                                 root = errand.value( "ssh_root", "/home/me/proj" ) ) ] )
